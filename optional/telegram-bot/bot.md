# fxbot conventions: the bot

What a change to the bot follows, besides what every change does ([docs/conventions.md](../conventions.md)).

## Telegram

- Callback data uses aiogram `CallbackData` subclasses with short prefixes. Telegram limits callback data to 64 bytes.
- Handlers stay thin; conversation state lives in FSM storage, not in memory.
- Each feature is a module in `fxbot/bot/routers/` exposing `create_router() -> Router`, included in `build_dispatcher`. Never a module-level router object: aiogram lets a router belong to one dispatcher only, and tests build a dispatcher per test.
- Handlers receive dependencies by parameter name from the dispatcher's data: `i18n`, `clock`, `settings` (always), plus from the middlewares:
  - `session`: the update's `AsyncSession`. The whole update is one transaction: committed when the handler returns, rolled back if it raises. Handlers don't call `commit()`.
  - `user`: the sender's `User` row (created on first contact).
  - `t`: the `Translator` for the user's stored language.
- "ℹ️ How it works" (`/help`, `fxbot/bot/routers/help.py`) explains the bot to users in short questions and answers. When a change alters what users can do, a limit or a timing, or how their data or chat is handled, update the matching answer too; numbers come from `Settings`, never typed into the text. Each answer is its title, then "•" points with a blank line between, what matters most in each in bold (#504, as is the greeting it shares, ST-2); a line may lead into the points (#558).
- Using the bot needs a verified phone: `User.is_onboarded` is the profile (`has_profile`) plus `phone_verified_at`. Link numbers only through `PhoneService`: `link_telegram_number` (the user's own Telegram contact, no code), or `send_code` then `confirm` (an allowed country, a mobile, one number per account, rate-limited; `confirm` returns a `CodeCheck` rather than raising for a wrong code, so the try is counted). Never store the number: only `phone_hash` (keyed fingerprint) and `phone_country`; while the code is on its way the conversation state holds the number sealed (`PendingPhone`). Codes go out through `fxbot/sms.py`: a `CodeSender` (the bot makes the code and keeps its HMAC: the Android gateway, or the console in development) or a `PhoneVerifier` (Twilio makes and checks it). In tests `FakeSender` and `FakeVerifier`; `BotTester.share_contact(user, own=True)` is the Telegram button. Browsing and `/help` need no phone. Test users from `make_onboarded_user` have one; in bot tests `BotTester.verify_phone(user)` types the number and `FakeVerifier`'s code, in service tests `tests.factories.verify_phone`.
- In-person exchanges (`ExchangeMode.IN_PERSON`, the default) may have a location check, and nothing needs one (#589): two switches of the dashboard's ⚙️ Settings → Location (`location_ask_posting`, `location_ask_responding`, off by default) make the bot ask on SH-1 before posting or responding, and "⏭️ Skip for now" goes on as sharing does. `LocationService.asks(user, Asking.…)` says whether to ask (the switch on, no check that still counts); `current(user)` is that check, if recent and not in a restricted country (`FXBOT_RESTRICTED_COUNTRIES`, #216; not necessarily the offer's country). The bot asks with `require_located(..., asking, resume)` (location_check router, a detour with a ResumeTarget, like onboarding), and both buttons resume. A check that counts stamps the offer (`location_checked_at`: its card says "✅ location checked") or the response (`location_checked_at`, `located_country`: RE-1 lists those from the offer's country first, after VIP ones). The check takes the user's own location: "📍 Share my location" under the message box sends it in one tap (Telegram has no button for a live one), a live location works too, a forwarded one doesn't. Live locations are for the meeting itself (deal_meeting). Never store or log coordinates: only `located_country`/`located_at` and `location_checked_at`. Country lookup is offline (`fxbot/domain/geo.py`). Test users from `make_onboarded_user` are located in their country at the fake clock's start; in bot tests `BotTester.share_location(user, PRAGUE)` (the key) or `share_live_location`.
- New commands are added to `bot_commands()` in `fxbot/bot/commands.py`, so they appear in Telegram's command menu in both languages; `tests/bot/test_commands.py` checks each one has a handler.
- Refusals are exceptions: services raise an `FxBotError` subclass from `fxbot/errors.py` (`ValidationError`, `LimitExceeded`, `NotAllowed`, `InvalidState`, `NotFound`) with an i18n key and params, e.g. `raise LimitExceeded("error-quote-limit", {"limit": 5})`. The bot rolls back just the handler's changes and shows the translated text (an alert for button presses). Handlers don't catch these themselves.
- Any other exception is a bug: the whole update is rolled back, it's logged with its `update_id`, and the user sees `error-unexpected`.
- Conversation state (aiogram FSM) lives in the `fsm_states` table via `PostgresStorage` and is committed on its own, independent of the update's transaction. Store only JSON-friendly values in FSM data (amounts as strings, not `Decimal`).
- `/cancel` is handled before any other router, so it always escapes a conversation.
- Router order in `build_dispatcher`: `cancel` first, feature routers, then `fallback` last (it answers unknown text with a hint and stale buttons with "no longer active"). Tests pass their own routers as `build_dispatcher(deps, test_router)`, which puts them before the fallback.
- Callback data classes shared by several routers live in `fxbot/bot/callbacks.py`. Buttons carry codes or indexes (e.g. into a list stored in FSM data), never free text: Telegram caps callback data at 64 bytes.
- When a button's step is done, remove its keyboard with `close_buttons(callback)` and always `await callback.answer()`, once: Telegram refuses a second answer to the same tap, so a handler that calls another answering handler doesn't answer again. Reply with `fxbot.bot.replies.answer(event, text)`, which works for a message or a button press alike.
- To show a new screen in place of the pressed message, use `edit_or_send(callback, text, markup)`, never `message.edit_text` directly: it ignores Telegram's "message is not modified" (a double tap) and sends a new message when the old one can't be edited.
- The main menu (`fxbot/bot/menu.py`) is a persistent reply keyboard; add feature buttons to `main_menu()`. Match a button with `menu_button(i18n, "menu-…")`, which accepts its label in every language. Send the menu after a finished action; `menu_for(user, t)` hides it from users who haven't onboarded. A menu button sends its caption as text, and keyboards already in users' chats keep the old caption until the bot sends a new menu: when renaming one, add the old caption in every language to `FORMER` in `fxbot/bot/menu.py`, so it still works. The ➕ More key toggles MO-1 (`MoreMenu`, #393): tapped again, or when another main key (`MAIN_KEYS`) is tapped, it closes what's open; a new main key goes into `MAIN_KEYS`. Its open message is kept in its own slot of the chat's state, which `state.clear()` doesn't touch.
- Conversation steps that take typed input filter on `PLAIN_TEXT` (`fxbot/bot/filters.py`), so commands and menu buttons still work mid-conversation.
- A screen with several fields, like the new-offer form, is one message changed in place, not a run of questions: its buttons change the fields where they are (a choice swaps into the same keyboard). Only a screen that asks for input takes typing (a side's currency and amount, the note, the place; not the form itself, #198), and the typed message is then deleted either way; and a refused input shows on the form itself rather than as a reply below it. If something came below the form meanwhile, typing brings it back down (messages in a private chat are numbered in turn). The rules live in `fxbot/domain/quote_form.py`, the drawing in `fxbot/bot/render/quote_form.py`.
- Buttons play the roles Apple's Human Interface Guidelines give them, in Telegram's colours (`style`, constants in `fxbot/bot/styles.py`): `MAIN` (green) for the one thing a screen is for (post, agree, send, make the deal, the exchange happened, accept a change), at most one per screen (`tests/bot/harness.py` fails a test that shows two); `DESTRUCTIVE` (red) for what can't be undone (cancel an offer or a deal, block, delete), on the way in and on the confirmation; `ACCENT` (blue) for the option in force among several, also marked in its text for clients without colours ("• EUR" in a row of options, "✅ English" in a list), and for the main menu's way in ("📢 New offer"). An alert in one row reads [Cancel] [Do it]; a longer one stacks the action above the way back. **[◀ Back] and [✖️ Cancel] change the message they're on into the previous screen, whatever it was**: they send nothing new, delete nothing the user still needs, and never scroll the chat (#260). Back is always "◀ Back" (`button-back`), except back to the offer list (OF-3), which reads "◀ To offers" (`back_text()` in `fxbot/bot/keyboards.py`). A screen opened under ➕ More goes back to ➕ More; one opened from someone's card (👤 Info) goes back to the card. A button that does the same thing wherever it's shown is a class in `fxbot/bot/buttons.py` owning its caption, colour and target (`ChatButton`, `CallButton`, `MoreButton`, …; #322, #332): screens use it and never spell its caption, and a text quoting a caption refers to it (`{ participant-button }`), so changing one is one edit. Where Telegram needs a message to change the keys under the message box, that message stays: deleting it takes the keys away (#275). **The way back** (◀ Back, ◀ To offers, ✖️ Cancel / Not now / Decline, ↩️ No, keep it: `WAY_BACK_KEYS` in `fxbot/bot/keyboards.py`) **is always the first from the left in a row it shares** (#267); `tests/bot/harness.py` fails a test that shows it anywhere else. Each thing has its own icon.
- A place is picked on one country picker and one city picker, SH-2 and SH-3 (`fxbot/bot/place_picker.py`, #329), wherever it's picked: never a list of countries or cities of a screen's own. `CountryPicker` is the one reader of `FXBOT_FEED_COUNTRIES`; `CityPicker` shows `PlaceService.cities` (one ranking for everyone). A screen that picks a place has a `PlaceUse` subclass (registered in `factory.build_dispatcher`): its questions, its own buttons around the pickers (Keep, Back, 🌍 any), where they show, what a country tapped or typed does (`country_chosen`: its cities, and whatever else the use does with the country: 📋 Offers' `FeedPlaces` keeps the first one as the user's, #600) and what a pick does (`picked`). Where a country or a city may also be typed, it's a `ConversationPlaces` (`fxbot/bot/location_flow.py`), where a country named in full (`country_named`) comes before a town spelled the same (#330): start it with `begin(event, ctx, keep_country=..., keep_city=..., country=...)`; its FSM data lives under one key, so the caller's draft is untouched. Reuse this pattern for any step shared by several screens: one class for what's shared, one per screen for what isn't.
- Time limits are shown as waits, never clock times (we don't know the user's time zone): put a `datetime` in the error params and `render_error()` turns it into "3 h 10 min". Word such messages "…again in { $x }".
- Actions that need a finished profile start with the guard:
  ```python
  if not await require_onboarded(message, state, user, t, services, ResumeTarget("new_quote")):
      return
  ```
  and register how to come back once onboarding completes: `resume_registry.register("new_quote", handler)` where `handler(event, context: ResumeContext, **args)`. `ResumeTarget.args` must be JSON-friendly (it's stored in FSM data).
- Every update is processed at most once: `DedupeMiddleware` records `update_id` in `processed_updates` inside the update's transaction. A crash rolls the record back (a retry runs again); a refused `FxBotError` keeps it (the user already got the answer).
- Two run modes (`FXBOT_BOT_MODE`): `polling` for local development (it removes any leftover webhook first), `webhook` for production (`fxbot/bot/web.py`: aiohttp server on `FXBOT_WEB_HOST:FXBOT_WEB_PORT`, the Telegram secret header is required, and `GET /healthz` checks the database).
- Try webhook mode locally with a Cloudflare quick tunnel (installed: `cloudflared`, no account needed):
  ```
  cloudflared tunnel --url http://127.0.0.1:8080        # prints https://<random>.trycloudflare.com
  # then run the bot with FXBOT_BOT_MODE=webhook, FXBOT_WEBHOOK_URL=<that URL>/telegram/webhook,
  # FXBOT_WEBHOOK_SECRET=<random string>; switch back by starting it in polling mode.
  ```
- Bot tests use `tests/bot/harness.py`: `BotTester.send_command(user, "/start")`, `.send_text(...)`, `.press(user, callback_data)`, then inspect `.sent_texts(chat_id)`, `.last_markup(chat_id)`, `.calls(SendMessage)`. When a handler calls a Bot API method the harness doesn't know yet, add a fake result to `RecordingSession._fake_result`. Like Telegram, the harness rejects text that isn't valid Telegram HTML (escape every user-supplied value with `html.escape(value, quote=False)`) and an edit that changes nothing; `session.fail_next_send(chat_id, error)` and `session.fail_next_edit(chat_id, error)` simulate other failures.

## Screen IDs

Every screen of the bot has an ID such as `ST-1` or `DL-9` (two letters for the area, then a number), and [fxbot/i18n/screen_ids.py](../../fxbot/i18n/screen_ids.py) is their one list. The user names screens by these IDs, e.g. "DL-9: make the warning shorter".

- A new screen goes into the list in the same PR, with the translation that starts its message (`keys`). A screen whose text is shared with another screen (an offer's page, for its poster and for others) has no keys: the code that builds it names it with `t.screen("XX-n")` instead.
- Each screen names its parent, the screen whose button opens it (#344). After adding or moving a screen, or changing an English text, run `uv run python scripts/build_screen_map.py`: it redraws [docs/screen-map.html](../screen-map.html), the tree with a sample of each screen, and a test fails while that page is out of date.
- IDs never change. A new screen takes the next free number in its area; a removed screen's ID moves to `RETIRED` and is never reused. A test checks this.
- An admin or a tester (a role given in the dashboard) can turn on screen IDs for themselves in ⚙️ Settings → 🧪 Tester (SE-11, #344): the bot then starts each screen it shows them with its ID. Nobody else sees them.
